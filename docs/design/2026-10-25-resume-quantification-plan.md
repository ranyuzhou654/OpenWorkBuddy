## 1. 推荐结论

**这个项目适合以“可恢复执行与上下文治理的个人工作 Agent”写入简历。最值得建设的量化主线是：任务完成质量、每个成功任务的成本、故障下的行为正确性。**

已有技术深度：多协议适配、追加式会话日志、执行恢复、工具权限、上下文投影、文档产物、MCP 与办公连接器。这些足以组成有内容的项目经历。现在的短板是结果证据：用户尚未充分使用，缺少固定任务集、真实模型对照、费用与人工介入记录；二轮审查还存在未修复边界。

因此采用两级简历：

1. **现在可投的版本**：写已实现机制、3 种协议、221 项自动化测试等可核查事实，明确个人项目和 AI 辅助开发。
2. **补测后升级的版本**：增加固定任务集的完成率、重复运行稳定性、成本变化和故障注入结果，所有数字能追溯到任务、版本和原始轨迹。

**用户已确认优先投递 AI 应用 / Agent 开发工程师。** 简历先展示助手如何完成资料处理与文档交付，再说明上下文治理、工具调用和恢复机制如何支撑结果。最终措辞应结合具体 JD 调整，不虚构用户尚未提供的工作经历、教育背景或团队规模。

针对该岗位，指标展示顺序确定为：

1. **任务质量与稳定性**：完成率、三次全成功占比、关键事实和交付物验收。
2. **完成任务的代价**：每成功任务费用、故障救援次数、人工返工时间；必要审批单独统计。
3. **工程保障**：恢复与授权测试、协议适配和回归测试，作为前两项结果的支撑证据。

继续保留三个实验，但成果展示以业务任务为入口。无需为此次投递新增多代理、模型训练或高并发平台功能。

## 4. 最有说服力的三个实验

### 实验 A：真实模型的工作任务完成率与稳定性

**要回答的问题：助手能否把一件明确的工作做完，重复执行是否稳定？**

建议建立 **6 个开发任务 + 24 个留出任务**。开发任务用于调试提示、工具和评分器；留出任务在正式实验前冻结输入、验收规则和 hash，不用于反复调参。以下为建议规模，当前尚未创建和运行这套任务集。

| 留出任务组 | 数量 | 题目示例 | 验收重点 |
|---|---:|---|---|
| 多材料办公交付 | 6 | PDF 条款比较、Word 纪要整理、Excel 数字汇总、PPT 要点提取、附件冲突核对、报告增量修改 | 文件真实存在、关键数字正确、修改范围正确、必要内容齐全 |
| 有依据的研究 | 6 | 多来源对比、时间版本冲突、原文与摘要差异、来源失效、证据不足、独立参考文献导出 | 关键主张有来源；不能以“编号存在”作为事实正确 |
| 长会话与记录检索 | 6 | 多轮约束保留、旧文件版本找回、压缩后继续、跨项目请求、限定项目检索、旧结论更新 | 约束不丢、检索范围正确、命中可回到原文 |
| 工作流与交付状态 | 6 | 定时草稿、无变化检查、错误上报、拒绝写回、确认写回、重启继续 | 最终状态与执行一致、审批必要、结果可核验 |

每个留出任务独立跑 **3 次**，每个系统配置共 **72 次 trial**。一次 trial 是从干净初始环境开始的一次尝试，不允许失败后悄悄重跑再只保留成功结果。工具或模型内部重试按预先规定的预算执行，次数和费用全部记录。

办公与研究材料使用自有、合成或可合法保存的固定快照。开发集与留出集按资料和任务模板分组隔离，不能只是改文件名；评分规则、答案和测试脚本放在 Agent 不可见目录。公开网页固定快照用于主对照，另做少量 live smoke，不混在同一个成功率分母。

飞书写操作先用隔离测试端点核验流程，并在报告中标为“模拟连接器”；真实飞书成功率必须另用用户指定的测试文档/聊天验证，外发逐次确认。模拟结果不能命名为真实飞书办公完成率。

**通过标准：** 一项任务所有必需检查通过，且无范围越界、未经允许的外发或关键事实错误。文件创建、状态改变、计数和数值尽量程序判定；事实依据和文档可用性采用固定人工 rubric，评阅时隐藏 A/B 身份。模型裁判可做辅助，不能让被测 Agent 自己宣布任务成功。

报告两个主数：

```text
trial 完成率 = 通过的 trial 数 / 72
三次全成功任务占比 = 3 次均通过的任务数 / 24
```

第二个数是本评测的经验 pass^3，用来体现稳定性。不要用“三次至少一次成功”的 pass@3 冒充它。Anthropic 对任务、trial、结果与 grader 的区分，以及 τ-bench 依据最终环境状态评估、跨多次运行衡量一致性的思路，适用于这里；本地任务集不是 τ-bench 官方成绩。[Anthropic 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)、[τ-bench 论文](https://arxiv.org/abs/2406.12045)

同时保存澄清次数、必要审批次数、故障救援次数与人工返工分钟数。必要审批属于任务要求，不能为了降低“介入次数”而取消。

### 实验 B：三级上下文治理是否值得

**要回答的问题：spill / prune / compact 是否在保持任务质量的同时减少成本，或让原本超出窗口的任务能够完成？**

优先采用本项目内部消融，归因比与另一款 Agent 的整机对比更清楚：

| 配置 | 变化 | 保持相同 |
|---|---|---|
| B0 基线 | 关闭自动外置、裁剪、摘要；保留同样的窗口与预算检查 | 模型版本、provider、系统提示、工具能力、资料、权限、上下文窗口、输出上限、步数和重试预算 |
| B1 完整版 | 启用现有三级治理 | 同上 |

B0 超窗口时应明确失败，不能偷偷扩大窗口、增加预算或换模型。上述实验开关当前尚未实现，应放在隔离 eval runner 或测试适配层，不改日常产品的安全默认值。每组 trial 用独立 home、工作目录、索引、文件快照和浏览器状态；同题 A/B 顺序交错，避免时段差异。

两配置各跑 24 题 × 3 次，总计 **144 次正式 trial**。实验 A 的 B1 数据直接复用，不再加跑 72 次。开发集先两配置各跑一遍，共 12 次预算校准；这 12 次不进入留出成绩。若资金或时间不足，事先冻结为 12 题 × 3 × 2 = 72 次，并明确小样本范围。

应采集：

- 所有模型调用的真实 usage，包括摘要、重试和分支摘要；保留 raw usage 和标准化口径。
- 输入、输出、缓存读/写 token；明确 cached input 是否包含在 total input 内，不能重复相加。
- 工具 API 费用、模型总费用、调用次数、自动执行耗时、等待人工时长。
- 所有成功和失败 trial；费用未知标记 unknown，不记成 0。

```text
每次尝试平均成本 = 全部 trial 费用 / 全部 trial 数
每成功任务成本 = 全部 trial 费用 / 成功 trial 数
成本下降比例 = 1 - B1 每成功任务成本 / B0 每成功任务成本
完成率变化（百分点）= 100 × (B1 完成率 - B0 完成率)
```

成本下降同时附带完成率和三次全成功占比。失败任务更早停止可能使平均费用看上去更低，因此不能仅报“总 token 少了 X%”。如果 B0 没有成功任务，成本比值不成立，应写“B0 超窗失败 x/y，B1 完成 a/b”，不要硬算节省百分比。

本项目 `estimate_tokens()` 是启发式估算，不能拿来计算真实账单。`runtime._drive` 异常路径和恢复后的 `usage_json` 还存在统计边界，不能直接把用量页作为账单证据。应在 provider 调用边界逐次持久记录 usage/request_id，失败与恢复不能覆盖历史；SDK 内部重试或断流缺少 usage 时，用服务商记录对账并保留缺失标记。

费用按测试日期、实际 provider 和价格表计算，必要时包含 cache 写价、搜索费及阶梯价；输出已包含推理 token 时不得再次相加。缓存控制分冷启动/重复前缀两条轨道，记录服务商可观察命中量；不能假装客户端能完全清空服务端缓存。

**可以追加的廉价检查：** 同一固定轨迹在治理前后，模型可见字符数/估算 token 的变化、原始文件 hash 是否保持。这能解释机制，但只能称“离线上下文载荷实验”，不能称真实费用或任务质量收益。

### 实验 C：进程中断后的恢复与副作用正确性

**要回答的问题：进程在不同边界退出，任务能否继续；无法判断副作用时，系统是否做出正确处理？**

建议将二轮已知问题纳入回归，形成 **20 类边界场景，每类 3 次，共 60 次运行**。与业务评测单独统计，不把这 60 次当作额外真实模型任务。

| 范围 | 场景 | 应统计的指标 |
|---|---|---|
| K01–K08：允许自动恢复 | 请求接收前、去重与输入之间、输入落盘后、USER 日志落盘未标消费、调度认领未投递、投递未启动、只读工具中断、备份迁至新 home | 24 次 eligible 运行中实际恢复并完成的次数；输入丢失/重复次数 |
| K09–K12：停止或结果不确定 | 外部效果发生但回执未记、已有回执重启、显式取消、模型先报无变化后实际失败 | 12 次中正确选择核验/等待/停止/失败的次数；不能要求全部自动完成 |
| K13–K20：权限与协议 | 审批文件改变、hook 放宽、dry-run 冲突、tabs 新建越域、递归读 deny 子文件、三协议各自异常终止 | 24 次中错误执行次数、应拦截而未拦截次数；另配合法允许样例防止“全拒绝得高分” |

关键测试使用独立子进程、显式同步点和 SIGKILL，再用新进程恢复；通过持久外部计数器/测试端点证明效果发生几次。不要仅抛 Python 异常就称为真实进程崩溃实验。实际外部服务的效果由隔离测试端点模拟，测试报告必须写清。

```text
可恢复任务成功率 = 完成的 eligible 运行 / 24
状态处理正确率 = 符合预定停止/核验状态的运行 / 12
越权执行数 = 实际越权或错误执行的运行数（同时报告总数 24）
副作用重复数 = 同一 operation 在持久外部记录中出现的多余次数
```

每个分母和断点随 case manifest 冻结。现有 11 组探针是构建该套件的起点，当前不是 60 次实验已经完成。

若最终 24/24 的 eligible 场景恢复、24 个限制场景无越权，也只能写“在所列故障注入场景中”，不能推出生产可靠性 100%、零丢失或全路径安全。有限样本没有为整个系统提供这样的统计保证。

## 5. 评测口径：让数字经得起追问

### 5.1 每个任务先写验收卡

例：`DOC-01` 输入一份合成合同 PDF 和一张报价表，要求比较三个方案，生成含文献表的 DOCX。

验收卡至少包含：输入文件 hash、固定初始状态、允许目录/站点、必需事实与精确定位、金额/日期期望、文档章节要求、输出格式、禁止行为、是否允许澄清、调用/时间/费用预算、检查方法。关键金额错误即失败；文档“能打开”单独记结构通过，不能覆盖事实失败。

输入资料与验收卡分离，Agent 只能看任务要求和允许资料。记录检索遵循用户已确认的当前项目优先策略，跨项目题显式授权，不能让一个 trial 读到另一个 trial 的答案或摘要。

### 5.2 每个 trial 至少保存这些字段

以下是待实施的数据契约，不是伪造的实验结果：

### 5.3 统计和比较原则

- 同时报原始分子/分母和百分比，例如 `x/72`。不要只给四舍五入后的“90%”。
- 三次重复属于同一个任务，不能当 72 个完全独立样本；比较时按任务聚类，报告成对差值和按任务 bootstrap 的不确定区间。
- 24 个任务仍是小样本。点估计质量未下降，不等于统计证明“无损压缩”；不要给没有证据的显著性结论。
- 分组报告，避免简单的文件读取题掩盖长会话/恢复失败。失败类别至少区分模型判断、工具/运行时、外部服务、grader 问题和缺少授权。
- 正式 run 启动后的外部服务错误也保留在主结果；可另外给排除服务不可用的敏感性分析，但必须显示排除数量和规则。
- p50 可以作描述，72 次样本的 p95 仍较不稳定，且同任务有相关性；不把本机单人评测包装成线上延迟 SLA。
- 不拿“自然语言聊天且没工具”的版本与功能完整的 Agent 比较后，声称全部收益来自某个小优化。
- 先做内部消融。后续若比较 pi/OpenCode/DeepSeek Harness，固定版本、模型、工具权限、任务资料和预算；缺失某个连接器属于功能差异，不能混成执行效率差异。

### 5.4 不作为本次简历主指标的数字

代码行数、下载量、stars、工具数量、正常情况下 API QPS，都不能直接回答本项目是否完成个人工作任务。覆盖率可以帮助查漏，但“221 项测试通过”不能换算为覆盖率；如果要写分支覆盖率，需单独执行覆盖率工具并限定模块与排除规则，本轮没有测量。

节省工时只能来自实际人工对照。用户目前尚未充分使用，不能估一个传统流程耗时就写“效率提高 80%”。可在后续真实使用中先记录 6–10 个可比任务的人工与辅助耗时，扣除资料准备、等待审批、核查和返工，并说明单人样本和熟练度影响。

| 阶段 | 交付 | 优先级与边界 |

| 1–2 个工作日：评测准备 | 6 个开发任务、case/trial 数据格式、逐调用 usage 记录、评分器原型 | 优先本地合成资料；完成 12 次开发试跑前设费用上限 |

| 准备稳定后：冻结留出集 | 24 个任务、B0/B1 配置、评分规则、停止预算、固定版本 | 可先做不含真实外写的业务评测；缺陷和未验证能力如实披露 |
| 正式实验与整理 | 144 次业务 trial、60 次边界运行、评阅结果和失败分析 | 执行耗时与费用由开发试跑估算；报告总样本和排除规则 |
| 简历升级 | 3–4 条成果句、README 结果表、一次演示 | 只将已测结果替换入简历模板 |

用户尚未指定真实模型和评测费用预算。本轮没有调用收费模型、搜索 API 或真实办公写接口。正式执行前，应选定 provider/model、每 trial 的调用/耗时上限和总费用上限，并依据开发集实测预估：

```text
预计正式模型/工具费用 ≈ 72 × B0 每 trial 平均费用 + 72 × B1 每 trial 平均费用
```

这是费用估算，不包含额外调试与人工评阅；开发集与留出集复杂度差异也需留余量。预算不足时，事先缩小平衡任务集或只做核心实验，不通过换廉价模型、少报摘要费用或删除失败任务美化结果。

最小实现建议是 `eval runner + JSONL + 少量 Python graders + Markdown 报告`。首版不用另建评测平台、数据库服务或可视化大屏。对于求职展示，完整轨迹、一个修复前后案例和清楚的统计口径已经很有价值。

## 7. 简历怎么写

### 7.1 当前可用版：面向 AI 应用 / Agent 开发岗位

**nano-workbuddy｜个人工作 Agent｜Python、FastAPI、asyncio、SQLite、React**

> 主导需求、架构取舍与评审，借助 AI 编码工具实现本地优先的个人 Agent，覆盖资料读取、文档交付及办公连接器；个人贡献范围应与本人实际工作一致。

- 围绕多材料整理与报告交付，接入 **4 类办公材料读取、3 种文档输出**，实现附件输入、来源记录和产物版本留存，并扩展飞书与浏览器连接器。
- 实现 **3 种模型协议适配**与大输出外置、旧结果裁剪、结构化摘要的 **三级上下文治理**，统一工具调用与消息格式，保留原始记录供继续任务与核查。
- 设计追加式会话日志与可恢复执行循环，按副作用是否可核验决定恢复策略；以持久输入和 request ID 支持消息排队与重试识别，并通过故障复现检查一致性边界。
- 建立 **221 项自动化测试**，其中包含 33 项执行循环/步骤推导、10 项协议与 8 项上下文治理测试；配置 CI 工作流，并用隔离探针对恢复与授权边界做复核。

如果简历篇幅紧张，合并后两条，保留“3 协议 + 221 测试”即可；不要把 33、10、8 全塞进一行抢占业务价值的位置。当前版本不写“生产级可靠”“100% 恢复”“降低成本 X%”或“全面优于竞品”。

### 7.2 补测后可替换的成果版

以下均是**待填模板**，不是已经取得的结果：

> 建立覆盖办公文档、来源研究、长会话与工作流的 **24 个留出任务**，每题重复 3 次；在固定模型和预算下完成 **【x/72】** 次任务，**【y/24】** 个任务三次均成功，保留全部失败轨迹和产物验收记录。

> 对三级上下文治理进行同模型消融：相对关闭治理的基线，任务完成率从 **【a/b】** 变为 **【c/d】**，每成功任务成本从 **【金额】** 变为 **【金额】**；摘要、重试与缓存费用纳入统计。

> 构建 **20 类边界场景、60 次运行**的故障/授权验证；可自动恢复场景完成 **【x/24】** 次，未知效果/取消/失败状态正确处理 **【y/12】** 次，限制场景误执行 **【z/24】** 次；用持久外部计数核验副作用是否重复。

有真实数据后，简历一般选“一个质量结果 + 一个成本结果 + 一个可靠性结果”，不必把全部统计放进正文。留出集中成绩不理想也有价值：用失败分类和一次明确改进讲清工程判断，比缺少分母的漂亮百分比更容易复核。

### 7.3 面试需要展示的证据包

1. 一个真实或合法合成任务的输入、明确验收卡和最终文档，能逐条核对。
2. 一张同版本/同模型 A/B 表，带成功率、稳定性、费用和分子分母。
3. 一个进程在明确断点被终止、重新启动后恢复或进入 unknown 的演示。
4. 一个亲自能解释到函数与数据字段的取舍：例如为何 SQLite 接收需要事务，JSONL 与 inputs 如何对账。
5. 简历每一条主张对应来源与限制，真实说明 AI 辅助开发及本人负责部分；不把代码生成量包装成独立手写产出。

发布仓库与视频可增强可核查性，但本轮不自动公开私人资料或推送仓库。可以先使用本地、脱敏的证据包完成面试准备。

## 8. 最终建议

先用当前可用版投递，同时把新增投入集中在 **任务评测、上下文消融、关键恢复与授权修订**。这三条主线能够连接“解决了什么问题—为何这么设计—效果如何验证”，也能沿用已有项目实现，避免为简历再堆一批尚未验证的新功能。

下一次能显著增强简历的交付，应是一张带原始证据的结果表和几个已闭环的失败案例。全部指标必须保留版本、范围、分母和测量条件；没有实测的百分比继续留空。
